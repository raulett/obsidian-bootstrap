# Second Brain - стартовый шаблон

Преднастроенное хранилище [Obsidian](https://obsidian.md) для ведения личной базы знаний (*second brain*) с поддержкой работы AI-агента. Вместо "голого" Obsidian вы сразу получаете рабочую структуру папок, набор плагинов, единые конвенции ссылок и дат, синхронизацию через Git и готовые инструкции для AI - из коробки в формате Claude Code, но шаблон не привязан к конкретному харнесу (годится и Codex).

База знаний управляется **в две руки**: вы - через интерфейс Obsidian, AI-агент - через файловую систему.

Он рассчитан на тех, кто хочет быстро начать работать в Obsidian, не настраивая его с нуля. Это **рекомендация, а не жёсткая схема**: любую папку, файл или настройку можно изменить или убрать под себя. Смотрите рекомендации ниже.

## TL;DR - что внутри

- **Структура папок** под методику second brain: входящие, база знаний, проекты, справочник со сроками годности, архив - и карты контента, связывающие всё в навигируемое дерево.
- **Несколько community-плагинов** + донастроенные core-плагины (Bases, Canvas, Templates). Минимальные базовые удобства, которых нет в коробочной версии.
- **Единые конвенции:** Markdown-ссылки с абсолютным путём, вложения в `_files/`, автоведение дат во frontmatter.
- **Git-версионирование** через плагин: автокоммит через 15 минут после последней правки, без автоматических pull/push - синхронизация с remote вручную.
- **Готовность к AI:** инструкции `CLAUDE.md` и скиллы в `.claude/skills/` - из коробки под Claude Code; для Codex и других агентов те же файлы доступны через `AGENTS.md` и `.agents/skills/`.

## Установка

### Шаг 1. Установите Obsidian

Скачайте и установите Obsidian для своей ОС с [obsidian.md/download](https://obsidian.md/download).

### Шаг 2. Получите шаблон (без git-истории)

Шаблон лежит на GitHub: [raulett/obsidian-bootstrap](https://github.com/raulett/obsidian-bootstrap). Вам нужна **рабочая копия без истории** репозитория-шаблона - дальше вы ведёте её в **своём личном** репозитории.

**Вариант А - скачать архивом (проще):**

1. Откройте [репозиторий шаблона](https://github.com/raulett/obsidian-bootstrap) на GitHub.
2. Нажмите **Code → Download ZIP** или скачайте [архив ветки `main`](https://github.com/raulett/obsidian-bootstrap/archive/refs/heads/main.zip) напрямую.
3. Распакуйте в папку будущего хранилища, например `~/Second-Brain`.

**Вариант Б - через git с удалением истории:**

```bash
# 1. Поверхностный клон (только последний коммит)
git clone --depth=1 https://github.com/raulett/obsidian-bootstrap.git ~/Second-Brain
cd ~/Second-Brain

# 2. Отвязать от шаблона - удалить его историю
rm -rf .git          # Windows (PowerShell): Remove-Item -Recurse -Force .git

# 3. Начать свою историю и подключить ЛИЧНЫЙ репозиторий
git init
git branch -M main
git remote add origin <URL-вашего-личного-репозитория>
git add .
git commit -m "init: second brain from bootstrap"
git push -u origin main
```

> Подключайте **свой** репозиторий, а не шаблонный: `origin` должен указывать на **ваш личный** репозиторий, иначе вы рискуете запушить личные заметки в общий шаблон. Личный репозиторий заранее создайте на GitHub (или там, где вам удобно) **приватным** и **пустым** - без README, `.gitignore` и лицензии: иначе в нём уже будет коммит, и первый `git push` отклонят. Не используйте кнопку **Fork**: форк публичного репозитория на GitHub тоже публичный и остаётся связан с шаблоном.

### Шаг 3. Откройте папку как хранилище

В Obsidian: **Open folder as vault** → выберите папку из шага 2.

При первом открытии Obsidian спросит про сторонние плагины - нажмите **Trust author and enable plugins** (выход из Restricted Mode). Плагины уже перечислены в шаблоне и включатся автоматически - кроме **Git**: он намеренно оставлен выключенным, чтобы не синхронизировать хранилище до того, как вы подключите свой репозиторий. Его вы включите вручную на шаге 4.

После первого запуска проверьте обновления и убедитесь, что плагины включены: **Settings → Community plugins** → **Check for updates** (при наличии - **Update all**), затем пробегитесь по списку и включите те, что остались выключенными.

### Шаг 4. Проверьте синхронизацию

После настройки git (шаг 2) и первого запуска **убедитесь, что плагин Git включён**: **Settings → Community plugins** → найдите **Git** и включите его, если он выключен. Без включённого плагина автоматические коммиты работать не будут.

Плагин **Git** настроен на **локальный режим**: он сам коммитит изменения через 15 минут после последней правки, но к remote не обращается - автоматических `pull` и `push` нет. Меняйте заметки, ничего не нажимая, - история правок копится локально. Отправить изменения в репозиторий: палитра команд → `Git: Push`; забрать правки с другого устройства: `Git: Pull`.

> [!tip] Включить автосинхронизацию
> Если нужна полная автоматика, в **Settings → Git** включите **Push on commit-and-sync** и **Pull on commit-and-sync**, задайте **Auto pull interval** (например, 15 минут) и **Pull on startup**. В файле настроек это `disablePush: false`, `pullBeforePush: true`, `autoPullInterval: 15`, `autoPullOnBoot: true`.

> Возможны merge-конфликты
> При расхождении истории (например, правки с двух устройств или чужой push) `pull` выдаст merge-конфликт и **не разрешит его сам** - это придётся сделать вручную через git-клиент. Если работаете с нескольких устройств, перед началом работы делайте `Git: Pull`, а закончив - `Git: Push`.

### Шаг 5 (опционально). Настройте AI-агента

См. раздел [Работа с AI-агентом](<#работа-с-ai-агентом>) - там установка CLI и обзор скиллов.

## Обновления и автономность копии

Централизованного обновления шаблона **не предусмотрено и не планируется**. Как только вы развернули копию (шаг 2), она становится **изолированной**: дальше вы сами распоряжаетесь настройками, своими записями, структурой хранения и набором расширений - подстраивайте всё под себя.

В каждой папке шаблона лежит короткий `README.md` с описанием её назначения, а в корне - файл `theme-preview.md` со всеми элементами разметки для проверки оформления тем. Это вспомогательные файлы: их можно спокойно удалить, переименовать или перестроить всю структуру директорий под себя.

Если в шаблоне появилось обновление, которое вам интересно, накатывать его вручную не нужно - просто попросите AI-агента перенести нужные изменения в вашу копию.

При всей свободе ради сохранности данных и совместимости рекомендуется придерживаться трёх вещей:

- **Бэкапьте всё в свой личный git-репозиторий** - это и так делает плагин Git (см. шаг 4), не отключайте его.
- **Не меняйте формат ссылок** (Markdown + абсолютный путь от корня) - иначе ломается совместимость с git-инструментами и AI.
- **Оставьте включённым плагин автоведения дат** (Frontmatter Date Manager) - на нём держатся поля `created` / `updated`.

## Как пользоваться (метод second brain)

База - это не свалка файлов, а растущий граф связанных заметок. Рабочий цикл:

1. **Захват.** Всё новое и недодуманное - в `inbox/`. Не раскладывайте преждевременно.
2. **Разбор inbox.** Периодически разбирайте входящие: дробите на атомарные заметки, добавляйте ссылки на связанное, переносите "вечнозелёное" в `Знания/`, проектное - в `Проекты/`, замыслы без срока - в `Проекты/Когда-нибудь/`, справочные материалы со сроком годности - в `Справочник/`.
3. **Связывайте.** Стройте граф Markdown-ссылками между заметками - связи ценнее тегов и папок.
4. **Архивируйте, не удаляйте.** Потерявшее актуальность переносите в `archive/`.
5. **Ресёрч.** Изучая тему, собирайте источники и сохраняйте готовую заметку в `inbox/`.

### Структура папок

| Папка         | Назначение                                                                                                     |
|---------------|----------------------------------------------------------------------------------------------------------------|
| `inbox/`      | Входящие: быстрый захват, неразобранные черновики, результаты ресёрча.                                         |
| `Знания/`     | Постоянная база знаний: атомарные "вечнозелёные" заметки, по подпапке на сферу жизни.                          |
| `Проекты/`    | Проектные заметки и материалы, по подпапке на проект; `Когда-нибудь/` - замыслы без срока.                     |
| `Справочник/` | Справочные материалы со сроком годности (поле `expires`, тег `type/reference`); истёкшее уходит в `archive/`. |
| `archive/`    | Устаревшее - не удаляем, а архивируем.                                                                         |
| `dashboards/` | Сводные представления Bases: разбор инбокса, активность, сроки, замыслы.                                       |
| `_files/`     | Вложения (картинки, PDF). Скрыта из навигатора.                                                                |
| `templates/`  | Шаблоны заметок и канваса.                                                                                     |

### Карты контента

Каждая папка с заметками получает **карту контента** - заметку-оглавление `Карта — Имя.md` с тегом `type/moc`: пара предложений о том, что это за предмет, и ссылки на все заметки и подразделы с кратким комментарием к каждой. Точка входа - корневая [Карта — Хранилище](</Карта — Хранилище.md>), закреплённая в навигаторе; от неё по картам разделов можно спуститься к любой заметке. Подробные правила (как называть, что перечислять, как карта проекта ссылается на профильные знания) - в [`CLAUDE.md`](</CLAUDE.md>).

### Сроки годности

Материал, который однажды заведомо устареет (тариф, условия договора, порядок из регламента), получает во frontmatter поле `expires` с датой. Дашборд `Сроки.base` собирает всё с `expires` по базе - ближайшая неделя, месяц, просроченное; `Справочник — сроки.base` - то же только по справочным материалам. Так напоминание о сроке живёт рядом с самим материалом, а не в отдельном календаре.

## Чем шаблон отличается от коробочного Obsidian

Все отличия подчинены одной задаче: база должна оставаться связной и переносимой - одинаково удобной и вам в интерфейсе, и AI-агенту через файлы.

**Ссылки и раскладка.** Внутренние ссылки - обычные Markdown-ссылки с абсолютным путём от корня, а не wikilinks, как в Obsidian по умолчанию. Они читаются как простой текст и вне Obsidian, не засоряют git-диффы и понятны AI-агенту, а при перемещении и переименовании заметок ссылки вместе с вложениями автоматически остаются в порядке. Новые заметки сразу создаются в `inbox/` - единой точке захвата, не нужно каждый раз выбирать папку; вложения уходят в скрытую `_files/` и не зашумляют дерево; удалённое отправляется не в системную корзину, а в локальную внутри хранилища - так его проще вернуть.

**Внешний вид.** Вместо дефолтной темы - Tokyo Night с фирменным акцентом и лёгкой прозрачностью, единый узнаваемый вид из коробки. Ограничение читаемой ширины строки снято, поэтому под широкие таблицы и представления Bases остаётся всё окно.

**Что включено в ядре.** Из встроенных модулей активно ровно то, что нужно базе знаний: Bases (табличные и карточные представления `.base`), Canvas, шаблоны, свойства, оглавление и закладки. Всё лишнее - ежедневные заметки, веб-вьюер, слайды, диктофон и прочее - выключено, чтобы не отвлекать; платные Publish и Sync тоже, их роль берёт на себя Git.

**Плагины-помощники.** Поверх ядра - дюжина community-плагинов, закрывающих то, чего в коробке нет: удобный файловый навигатор, мгновенный полнотекстовый поиск, автоведение дат во frontmatter, работа с Markdown-таблицами, автоформатирование заметок при сохранении. Отдельно стоит версионирование: плагин Git сам коммитит правки, так что история заметок копится без ручных коммитов, а в репозиторий она уходит по вашей команде, а Local REST API даёт AI-агенту канал для поиска по базе. ## Работа с AI-агентом

Шаблон рассчитан на то, что часть рутины ведёт AI-агент: захват, структурирование, связывание и поиск по базе. Канонические конвенции хранилища и инструкции для агента лежат в [`CLAUDE.md`](</CLAUDE.md>). Из коробки шаблон заточен под **Claude Code** - он подхватывает файл автоматически из корня, - но харнес не зашит жёстко: ниже описаны три варианта - Claude Code, Codex и Claude Desktop.

### Claude Code (из коробки)

**Claude Code** - официальный CLI Anthropic. Установите по инструкции [docs.claude.com/claude-code](https://docs.claude.com/en/docs/claude-code). Он автоматически подхватывает `CLAUDE.md` и скиллы из `.claude/skills/`.

Запускайте CLI из корня хранилища - тогда агент видит инструкции и работает по конвенциям базы.

### Codex и другие агенты

Codex CLI (агентский CLI от OpenAI) и совместимые с ним агенты читают не `CLAUDE.md`, а `AGENTS.md`, и ищут скиллы не в `.claude/skills/`, а в `.agents/skills/`. Формат `SKILL.md` - открытый стандарт, который понимают и Claude Code, и Codex, поэтому в шаблоне ничего не дублируется: `AGENTS.md` - симлинк на `CLAUDE.md`, а `.agents/skills/<имя>` - симлинки на `.claude/skills/<имя>`. Инструкции и скиллы подхватываются из коробки, а правите вы только файлы Claude Code. Добавили новый скилл - заведите для него симлинк в `.agents/skills/`.

> [!warning] Windows
> Git на Windows по умолчанию превращает симлинки в текстовые файлы с путём внутри. Клонируйте с `git clone -c core.symlinks=true ...` (нужен режим разработчика или права администратора) - иначе Codex увидит вместо инструкций одну строку `CLAUDE.md`.

Без переноса остаются MCP-серверы (у Codex свой конфиг `.codex/config.toml`) и личные инструкции из `CLAUDE.local.md`. MCP-конфиг можно поручить перенести официальному скиллу Codex `migrate-to-codex`: он сканирует `.claude/` и пишет результат в нативные форматы Codex. Важно: `AGENTS.md` и `.agents/skills/` - симлинки, и запись в них попадёт прямо в `CLAUDE.md` и `.claude/skills/`, поэтому в промпте их нужно явно исключить. Откройте корень хранилища в Codex и дайте такой промпт:

```
Установи и запусти официальный скилл Codex migrate-to-codex ($skill-installer migrate-to-codex),
чтобы перенести MCP-серверы из .mcp.json (.mcp.json.template) в нативный конфиг Codex
.codex/config.toml. AGENTS.md и .agents/skills/ уже есть - это симлинки на CLAUDE.md
и .claude/skills/: их не создавай, не перезаписывай и не правь. CLAUDE.local.md в AGENTS.md
не переноси - если файл есть, предложи в отчёте, куда его положить. Исходные файлы
Claude Code не трогай. Доведи миграцию до конца сам: scan → dry-run → запуск →
правка блоков "MANUAL MIGRATION REQUIRED" → validate, не останавливаясь на промежуточных
шагах. В конце покажи отчёт - что перенесено, что требует ручной проверки
и что не имеет аналога в Codex.
```

После миграции проверьте `git status`: `CLAUDE.md` и `.claude/skills/` должны остаться без изменений, а MCP-серверы из `.mcp.json` - появиться в `.codex/config.toml`.

### Claude Desktop (режим Code)

Claude Desktop (GUI-приложение) - не только чат. У приложения три режима (табы вверху окна): **Chat**, **Cowork** и **Code**. Для работы с хранилищем используйте таб **Code** - это тот же Claude Code, что и в терминале, только с графическим интерфейсом.

### Как агент пишет в базу

Агент читает и пишет `.md` напрямую через файловые инструменты - проще, быстрее, работает и при закрытом Obsidian. Запущенный Obsidian мгновенно подхватывает изменения на диске, поэтому агент сверяется с актуальным состоянием файла перед правкой.

Для **поиска** по базе агент использует MCP-сервер `obsidian` - это дополнение к файловому доступу, а не замена: запись по-прежнему идёт файлами. Что он умеет и как его подключить - в следующем разделе.

### MCP-сервер

MCP - дополнительный канал агента поверх файлов: релевантный поиск по базе и операции, которых нет у файловых инструментов. Запись в базу всё равно идёт файлами, MCP её не заменяет. В шаблоне один сервер - **`obsidian`**: Omnisearch (релевантный полнотекстовый поиск, точнее grep), навигация по секциям заметки, теги, frontmatter, команды Obsidian.

`obsidian` работает поверх плагина Local REST API и отвечает, только пока запущен Obsidian; закрыт - поиск идёт через файловые инструменты (штатный фолбэк).

#### Настройка

`.mcp.json` не версионируется (в нём могут оказаться личные креды, если вы добавите свои серверы), поэтому в шаблоне лежит заготовка **`.mcp.json.template`**. Скопируйте её и перезапустите Claude Code / Codex - без этого шага сервер не поднимется:

```bash
cp .mcp.json.template .mcp.json
```

`obsidian` работает из коробки: адрес и ключ - localhost, менять нечего.

**Свои серверы и креды.** Другие MCP-серверы (почта, календарь, вики и т.п.) добавляйте в `.mcp.json` сами. Значения в нём подставляются из окружения синтаксисом `${VAR:-дефолт}`, поэтому секрет достаточно задать переменной в шелле. bash / zsh (Linux, macOS) - строкой в `~/.bashrc` или `~/.zshrc`:

```bash
export MY_SERVER_API_KEY=your_api_key
```

Windows (PowerShell) - `setx` пишет в профиль пользователя, значение появится в **новых** окнах терминала:

```powershell
setx MY_SERVER_API_KEY "your_api_key"
```

Не хотите держать секрет в окружении - впишите значение прямо в `.mcp.json` вместо `${...}`: проще, но креды лежат в файле открытым текстом (файл неверсионный, в репозиторий не попадёт). Новый сервер включите в `enabledMcpjsonServers` в `.claude/settings.json`.

### Скиллы

Готовые навыки в формате `SKILL.md` - открытый кросс-агентный стандарт, его понимают и Claude Code, и Codex. Лежат в `.claude/skills/` и подхватываются автоматически; для Codex они же видны через симлинки в `.agents/skills/` (см. выше):

| Скилл                 | Назначение                                                                                              |
|-----------------------|---------------------------------------------------------------------------------------------------------|
| **obsidian-markdown** | Obsidian-разметка: коллауты, эмбеды, свойства/frontmatter (ссылки - markdown-абсолютные, не wikilinks). |
| **obsidian-bases**    | Создание и правка `.base` - табличных/карточных представлений.                                          |
| **json-canvas**       | Создание и правка `.canvas` - канвасов, mind map, схем.                                                 |
| **obsidian-cli**      | Уникальное из CLI: граф бэклинков, задачи, шаблоны, dev-слой (CRUD - файлами, поиск - через MCP).       |
| **defuddle**          | Чистый Markdown из веб-страницы для ресёрча (готовую заметку агент кладёт в `inbox/`).                  |
| **save-url**          | Сохранение страницы по ссылке целиком: заметка в `inbox/`, картинки в `_files/`, источник во frontmatter. |

### Frontmatter и даты - не редактируются вручную

Плагин **Frontmatter Date Manager** сам ведёт `created` и `updated` (формат `yyyy-MM-dd'T'HH:mm:ss`), пока Obsidian открыт. Исключения, которые плагин не трогает: `README.md`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` и всё в `.claude/`, `.agents/`, `.codex/`, `templates/`, `tmp/`.

### Личные инструкции для агента

То, что не должно уезжать в общий репозиторий, держите в `CLAUDE.local.md` в корне (он в `.gitignore`) - Claude грузит его автоматически рядом с `CLAUDE.md`. Через симлинк `AGENTS.md` он в Codex не попадает - см. раздел про Codex выше.
